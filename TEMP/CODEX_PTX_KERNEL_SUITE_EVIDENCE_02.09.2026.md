B) Paper-ready subsections (plain text with inline evidence pointers)

**B.1 Sovereign Hot Path and Why PTX Is Central**

Knowledgeverse explicitly defines a single persistent CUDA/PTX execution domain where active galaxies, TRM state, and learning buffers co-reside [docs/vocabulary/KNOWLEDGEVERSE_SPECIFICATION.md:36-40]. The spec’s sovereignty invariant names PTX kernel execution, Galaxy navigation, RPN execution, and TRM inference as allowed hot-path operations, while forbidding host-side scientific stack use in inference [docs/vocabulary/KNOWLEDGEVERSE_SPECIFICATION.md:259-277]. In implementation, this appears as a sovereign loader API (`load_ptx`, `load_ptx_file`, `get_function`, `launch`) that acquires kernel handles and launches device code via CUDA driver bindings [knowledge3d/cranium/sovereign/loader.py:257-333].

**B.2 Host Orchestration vs Device Execution (Current Code Reality)**

The codebase enforces a host/device split: Python wrappers perform orchestration (buffer prep, dispatch), while kernels perform vectorized compute. The modular RPN engine states this directly: Python is used for entrypoint and I/O; compute is in GPU PTX [knowledge3d/cranium/ptx_runtime/modular_rpn_engine.py:6-12]. The TRM launcher follows this pattern by loading fused and extension PTX kernels once and dispatching `matvec/swiglu/vec_add` kernels per refinement step [knowledge3d/cranium/sovereign/trm_launcher.py:125,234-246,260-320].

For ARC specifically, `ARCPTXOps` JIT-compiles a dedicated kernel set (`weighted_score`, `discovery`, `validity`, `compare_grids`) and adapter code routes discovery, ranking, validity gates, and fuzzy oracle checks through those kernels [knowledge3d/cranium/ptx/arc_ops.py:68-307,421-780; benchmarks/arc_agi_2_adapter.py:533-539,565-571,1155,1427-1434,1607-1617].

**B.3 Kernel Suite Breadth, Packing, and VRAM Discipline**

Repo enumeration currently finds 159 CUDA kernel occurrences and 158 unique kernel names in `knowledge3d/**/*.cu`, with 87 kernel names observed at load/dispatch call sites (`load_ptx_file`, `get_function`, `RawKernel`) [TEMP/kernel_names_unique.txt; TEMP/kernel_def_callsite_map.json]. The implemented suite is multi-family rather than monolithic: ARC scoring/oracle kernels, RPN execution kernels, TRM fused/extension kernels, modality encoders, geometry/spatial kernels, ternary arithmetic/codec kernels, and training kernels [knowledge3d/cranium/ptx/arc_ops.py:71-272; knowledge3d/cranium/kernels/modular_rpn_kernel.cu:175,821; knowledge3d/cranium/ptx/trm_extensions.cu:29-145; knowledge3d/cranium/ptx/modality_kernels.cu:36,132,276,423; knowledge3d/cranium/ptx/kernels.cu:1-149; knowledge3d/cranium/ptx/codec_ops.cu; knowledge3d/cranium/ptx/sgd_optimizer.cu].

Ternary compression and arithmetic are first-class in the suite (`ternary_add_kernel`, `ternary_mul_kernel`, quant/dequant + DCT/MDCT kernels), and are wired through sovereign launcher paths [knowledge3d/cranium/bridges/tiered_rpn.py:493-567; knowledge3d/cranium/codecs/ternary_codec_ops.py:1-31]. This aligns with the project’s VRAM-discipline positioning in docs (ternary/PTX/RPN emphasis), but exact throughput claims should remain tied to benchmark artifacts rather than generalized assertions [docs/vocabulary/SOVEREIGN_NSI_SPECIFICATION.md:586-589].

**B.4 Mapping to Knowledgeverse Concepts (Only Explicit Links)**

The spec explicitly connects hot-path PTX execution (Region 1), Galaxy navigation (Region 2), TRM inference (Region 5), and Shadow Copy recording (Region 6) in one loop [docs/vocabulary/KNOWLEDGEVERSE_SPECIFICATION.md:265-270]. Shadow Copy and SleepTime are defined as continuous learning during inference and two-phase consolidation respectively [docs/vocabulary/KNOWLEDGEVERSE_SPECIFICATION.md:892-931; 1027-1080]. Ingestion Stargate is explicitly outside hot path for host-side parsing, then crystallizes candidate RPN into Galaxy in idle/hot-path cycles [docs/vocabulary/KNOWLEDGEVERSE_SPECIFICATION.md:1169-1244]. These are the repo-grounded links for writing PTX/kernel architecture in paper form without importing unsupported claims.

**B.5 Positioning: DeepSeek single-kernel vs K3D kernel-suite (conservative)**

Repo evidence supports describing K3D as a kernel-suite architecture (many specialized kernels integrated under one sovereign runtime) rather than a single-kernel design [TEMP/kernel_def_callsite_map.json; knowledge3d/cranium/sovereign/loader.py:257-333]. The repository does **not** provide a primary-source citation for a specific "DeepSeek single-kernel milestone"; therefore any statement about that milestone should be marked external context and not treated as an internally supported claim. A safe paper phrasing is: K3D does not claim novelty in CUDA/PTX itself; its contribution is system-level integration of multiple kernel families (RPN, ranking, ternary codec, modality, spatial, TRM) within a sovereignty-constrained inference architecture [docs/vocabulary/KNOWLEDGEVERSE_SPECIFICATION.md:119-125; knowledge3d/cranium/ptx/arc_ops.py:68-307].
