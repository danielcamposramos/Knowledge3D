## Governing principle (do not violate)

- **Ingestion path is flexible.** ollama, numpy, sentence-transformers, HTTP requests — all allowed here. The sovereignty rule applies to the *output*: the stars that land in the VRAM table must be fully self-contained RPN + symlinks, with zero runtime external dependencies.
- **Star schema is law.** Use the MeaningCentricStar field set from §2.1 of the schema spec. Do not invent parallel field names.
- **Symlinks are always bidirectional.** If A references B, B references A. No exceptions. Enforced by a single `link(a, b, forward_kind, backward_kind)` helper — never write a one-sided reference.
- **Meaning at the center.** A concept star (e.g. `concept_digit_two`) exists once. `"2"`, `"two"`, `"dois"`, `"二"` are surface-form references, not separate stars.
- **Content-addressed IDs.** `star_id = ContentHash(meaning_rpn || meaning_class || domain)`. Rerunning the crafter with the same input must produce the same star_ids. Spec §8.1.
- **No benchmark names anywhere.** `math_operator_addition`, not `gsm8k_addition`. Schema §2.4.

## Scope (minimal, complete, composable)

Craft the smallest possible set of stars that lets `"2+3?"` solve end-to-end through the sovereign RPN path — and generalizes to arbitrary single-operator arithmetic of arbitrary-length integers out of the box.

### 6.B.1 — Digit concept stars (10 stars)

For each digit 0–9, one `concept` star:

- `meaning_class = concept`
- `domain = "Math/Number/Integer/Digit"`
- `meaning_rpn`: procedural definition — the numeric value pushed on the stack, plus taxonomy links (`even|odd`, `prime` where applicable)
- `surface_forms`:
  - `en`: word-star ref for `"zero"`..`"nine"`
  - `pt`, `es`, `ja`, `zh`, `ar` — at minimum English, leave the scaffold for others; ollama drafts the additional languages
  - `char_refs`: ref to the ASCII character star (`'0'`..`'9'` — already in Character Galaxy if present, otherwise crafted as a Layer 1 form star)
- `taxonomy_refs` → parent `concept_integer`, `concept_number`
- `embeddings`: Matryoshka tiers 64/128/512/2048, generated by the existing sentence-transformers ingestion path from a deterministic text template
- `selection_role = ROLE_ANSWER` (digit stars are answer-bearing)
- `answer_eligible = 1`
- bidirectional symlink: digit star ↔ digit character form star, digit star ↔ digit word form star

**Note:** the digit star does NOT carry an RPN program in `meta_rule_addr`. It *is* the value. The operator star's RPN program pulls operands from the query's ActionBuffer operand slots — not from the digit stars. Digit stars matter for cosine navigation (`"two"` query → lands on `concept_digit_two` → TRM knows the value is 2), not for execution.

### 6.B.2 — Arithmetic operator stars (5 stars)

For each of `+`, `-`, `*`, `/`, `^`, one `action` star:

- `meaning_class = action`
- `domain = "Math/Operator/Arithmetic"`
- `meaning_rpn`: procedural definition of the operation (what it does, domain, range)
- `surface_forms`:
  - `en`: `"plus"`, `"minus"`, `"times"` / `"multiplied by"`, `"divided by"`, `"to the power of"`
  - same multi-language scaffold as digits
  - `char_refs`: ASCII/Unicode symbol form stars (`'+'`, `'-'`, `'*'` / `'×'`, `'/'` / `'÷'`, `'^'` / `'**'`)
- **`meta_refs`**: symlink to one `rpn_program` star that holds the executable bytecode (see 6.B.4)
- `taxonomy_refs` → parent `concept_arithmetic_operator`, `concept_binary_operation`
- `selection_role = ROLE_EXECUTOR`
- `answer_eligible = 1`
- bidirectional symlinks: operator ↔ symbol form star, operator ↔ word form star, operator ↔ rpn_program star

### 6.B.3 — English number word stars (10+ stars)

`"zero"`, `"one"`, ..., `"nine"` as Layer 1 form stars in Word Galaxy. Each:

- `meaning_class = concept` (word = a form that references a meaning)
- **`surface_forms.en`** — this IS an English word
- **`taxonomy_refs`** → bidirectional symlink to the corresponding digit concept star

This is the bridge Daniel described: `"two"` and `"2"` and `concept_digit_two` all point to each other through symlinks. The TRM navigates from any surface form to the meaning.

### 6.B.4 — RPN program stars (5 stars)

Executable RPN bytecode lives in its own `rpn_program` stars, not inline on operator stars. Symlinked.

For each operator, one `rpn_program` star:

- `meaning_class = meta`
- `domain = "Programs/Math/Arithmetic"`
- `meta_rule_addr`: offset into the sovereign program table (allocated by `sovereign_hot_path.py`, see below)
- bytecode: minimal Math-tier sequence, e.g. for addition: `[OP_PUSH_OPERAND_0, OP_PUSH_OPERAND_1, OP_ADD, OP_STORE_RESULT, OP_RET]`
- bidirectional symlink back to its operator concept star

**Why a separate star**: Daniel's exact words — "carrying actual executable RPN (also symlinked)". Programs are shared, content-addressed, and reusable. The `add` program could be symlinked by the `sum` concept, the `+=` concept, the `increment` concept, etc. If programs were inline on operator stars we would duplicate bytecode across concepts. Schema §1.6 "reference pattern — no duplication".

### 6.B.5 — Grammar rule stars (5 stars)

Transformation rules as Layer 3 stars in Grammar Galaxy:

- `binary_op_infix`: `{operand_1} {operator} {operand_2}` → operand pack
- `binary_op_infix_eq`: `{operand_1} {operator} {operand_2} = {result}` → verify or solve
- `question_what_is`: `what is {expression}` → extract `{expression}` as subquery
- `english_binary_op`: `{word_operand_1} {word_operator} {word_operand_2}` → english surface form
- `trailing_question_mark`: `{expression}?` → strip punctuation, mark as question

Each grammar star:

- `meaning_class = meta`
- `meaning_rpn`: transformation program — consumes tokens, emits operand slots
- `grammar_refs`: bidirectional symlink to the operator/digit/word stars it applies to
- `selection_role = ROLE_ROUTER` (grammar stars route, not answer)

These are crafted by the ollama process — grammar rules are inherently pattern-driven and that is where the LLM specialist earns its keep.

### 6.B.6 — Program table (sovereign-side, not crafted)

This is *implementation*, not a crafted star — but 6.B cannot land without it.

- `sovereign_hot_path.py` allocates a VRAM-resident program table
- `TrmStepFusedBridge.bind_program_table(ptr, size)` exposes the pointer
- `HeadlessTabletMPC._bind_bridge_query_runtime()` binds the table alongside the Galaxy table
- The Star Crafter writes program bytecode into the table during ingestion; the table persists across ticks

Program table layout per entry: `[program_len: u16, opcode_count: u16, bytecode: u8[program_len], pad to 8]`.

## The Star Crafter itself

### File layout

New module: `knowledge3d/ingestion/star_crafter.py`

Parallel to `knowledge3d/ingestion/proceduralizer_stargate.py`. Uses the same augmentation provider pattern that H16/H16b/H16d established — default to the Ollama local provider, fall through to subscription/API providers only if explicitly configured.

### Architecture

```
star_crafter.py
├── class StarCraftRequest     # what to craft (digit/operator/word/grammar/program)
├── class StarCraftPlan        # structured output from ollama
├── class StarCrafter          # orchestrator
│   ├── __init__(provider, program_table, galaxy_table)
│   ├── craft_digit_stars()          # 10 stars
│   ├── craft_operator_stars()       # 5 stars + 5 program stars
│   ├── craft_number_word_stars()    # 10+ stars (en minimum)
│   ├── craft_grammar_rule_stars()   # 5 stars
│   ├── _dispatch_ollama(prompt)     # calls augmentation provider
│   ├── _validate_plan(plan)         # schema conformance
│   ├── _materialize(plan)           # writes star record into galaxy_table + bidirectional symlinks
│   └── _link(a, b, fwd_kind, bwd_kind)   # bidirectional link helper (THE only path for any symlink)
└── build_foundational_star_crafter_outputs() — entry point called from foundational_galaxy_builder.py
```

### ollama dispatch pattern

The Star Crafter uses the existing augmentation provider surface (H16 family) — do NOT invent a new HTTP client. Find the provider factory already wired for Ollama in the multi-provider augmentation path; reuse it.

Prompts are structured: the crafter asks for a JSON object matching `StarCraftPlan`, validates it against the schema before materializing, and rejects any free-form response. The ollama specialist's job is to *draft the linguistic surface forms, grammar transformation descriptions, and meaning text*, NOT to invent fields. Fields are fixed by the schema spec.

**Example prompt for a number word star (draft — refine in implementation):**
```
Craft a MeaningCentricStar for the English number word "two".
Output JSON only, matching this schema:
{
  "meaning_class": "concept",
  "domain": "Math/Number/Integer/Digit",
  "surface_forms": {
    "en": {"word": "two", "ipa": "tuː"},
    "pt": {"word": "dois", "ipa": "dojs"},
    "es": {"word": "dos", "ipa": "dos"},
    "ja": {"word": "二", "romaji": "ni"},
    "zh": {"word": "二", "pinyin": "èr"},
    "ar": {"word": "اثنان", "transliteration": "ithnan"}
  },
  "meaning_description": "The cardinal number 2; the integer following 1 and preceding 3.",
  "taxonomy_parents": ["concept_even_number", "concept_prime_number"]
}
```

The crafter validates this against a pydantic model before accepting. If the LLM hallucinates fields or omits required ones, the crafter retries or fails — never silently accepts.

### Why ollama and not hardcoded

Daniel's direction is explicit: a parallel ingestion process. There are three reasons this matters even for a tiny bootstrap set:

1. **Language coverage** — hardcoding 10 digits × 10 languages × 5 fields = 500 entries of brittle data. ollama drafts them correctly in one pass.
2. **Grammar rule patterns** — grammar transformations are where LLM specialists are legitimately useful; hardcoding the 5 rules would freeze the pattern language.
3. **Precedent for scaling** — once the crafter works for digits+operators+words+grammar, the exact same path extends to 176 math symbols, then 15k words, then 1k grammar rules (Phase C.4 in [docs/ROADMAP.md](../docs/ROADMAP.md)). This is the architectural beachhead for foundational knowledge ingestion.

### Bidirectional link helper

```python
def _link(self, star_a_id, star_b_id, fwd_kind, bwd_kind):
    """
    Write symlinks on both stars simultaneously.
    This is the ONLY path for any symlink in the star crafter.
    Any other symlink write path is a bug.

    fwd_kind / bwd_kind are from the schema's symlink taxonomy:
    - taxonomy_refs / taxonomy_refs
    - surface_forms.{lang}.word_ref / taxonomy_refs
    - meta_refs / grammar_refs
    - component_refs / composite_of
    - grammar_refs / taxonomy_refs
    """
    self._append_ref(star_a_id, fwd_kind, star_b_id)
    self._append_ref(star_b_id, bwd_kind, star_a_id)
```

Follow schema §2.1 for the valid `*_refs` field names. `component_refs` pairs with `composite_of` (the schema's canonical bidirectional pair).

### Content-addressed IDs

Per schema §8.1:

```python
def compute_star_id(meaning_rpn: bytes, meaning_class: str, domain: str) -> bytes:
    return blake3(meaning_rpn + meaning_class.encode() + domain.encode()).digest()[:32]
```

Rerunning the crafter must produce the same star_ids. Test for this — see 6.B validation below.

## Phase 6.B validation

New file: `tests/test_phase6b_star_crafter.py` under `K3D_PYTEST_PROBE_CUDA=1`.

1. **Minimum star counts** — after running the crafter, assert:
   - ≥10 digit concept stars
   - ≥5 operator concept stars
   - ≥5 rpn_program stars, each with `meta_rule_addr` != 0 pointing inside the program table
   - ≥10 english number word stars
   - ≥5 grammar rule stars
2. **Bidirectional symlink proof** — pick one random digit concept star. Assert:
   - it has an `en` surface form word_ref
   - the target word star has a `taxonomy_refs` entry pointing back at the digit concept
   - same for char_refs / char form stars
3. **Operator → program symlink proof** — the `add` operator star has `meta_refs` pointing to an `rpn_program` star, and that program star has `meaning_rpn` matching the Math-tier bytecode for addition, and `meta_rule_addr` points into the VRAM program table.
4. **Content-hash stability** — run the crafter twice with the same provider mock (deterministic JSON output). Assert star_ids are identical across runs.
5. **Sovereign field compliance** — all crafted operator stars have `selection_role == ROLE_EXECUTOR`, `answer_eligible == 1`, `meta_rule_addr != 0`. All digit stars have `selection_role == ROLE_ANSWER`, `answer_eligible == 1`.
6. **Cosine navigation sanity** — embedding of `"plus"` (via sentence-transformers, ingestion path) produces a top-3 cosine match containing the `add` operator star. Embedding of `"two"` produces a top-3 match containing `concept_digit_two`. This proves the cosine path would route correctly before 6.C even wires execution.

## The substrate this unlocks

Once 6.B lands, Galaxy navigation for `"2+3?"` produces the right hits by cosine alone — without execution yet:

- `"2"` → `concept_digit_two`
- `"+"` → `math_operator_addition`
- `"3"` → `concept_digit_three`
- `"?"` → `grammar_trailing_question_mark`

All four hits have `selection_role` set, `answer_eligible` on the relevant ones, bidirectional symlinks to their programs, and meaningful content-hash IDs. 6.C then only has to: (1) pack digits from the query into operand slots, (2) follow the operator star's `meta_refs` symlink to its `rpn_program` star, (3) call the sovereign device-local RPN executor with `meta_rule_addr` + operands, (4) write the result into the outgoing ActionBuffer.

That is the meaning-centric sovereign path Daniel described: *navigates the meaning-centric by semantic clue and executes the metadata with the RPN way of solving it*.
