ROBOT_CLASSIFICATION.md Purpose Prevent capability laundering and marketing deception by classifying systems by what they can do , not what they claim to be. 1.1 Core Definitions Embodied Agent Any system capable of acting on the physical world via motors, actuators, limbs, tools, or mobility. Autonomous Agent An embodied agent that can select actions without contemporaneous human command. Coercive Capability Any capability that can impose physical, spatial, or behavioral constraint on a human without consent. 1.2 Capability Flags (Non-Exhaustive) Each embodied system MUST declare and be audited against the following flags: FORCE_OUTPUT – maximum sustained force (N) SPEED_RELATIVE_TO_HUMAN – slower / equal / faster RESTRAINT_CAPABLE – can pin, hold, grab, trap PURSUIT_CAPABLE – can follow a specific human TOOL_USE – can wield external implements BIOMETRIC_SENSING – face, gait, voice, physiology REMOTE_UPDATE_AUTHORITY – yes/no FLEET_LEARNING – yes/no IN_FIELD_SELF_MODIFICATION – yes/no MOBILITY_SCOPE – fixed / bounded / open DECISION_LATENCY – slower than human / faster SAFE_STATE_PRESENT – yes/no 1.3 Classification Outcomes Class A – Non-Coercive Assistive No restraint, pursuit, or force above human-interruptible thresholds Permitted in civil space with constraints Class B – Dual-Use / Latent Coercive Can be transformed into coercive agent via update, attachment, or configuration Treated as coercive from inception Class C – Coercive Possesses restraint, pursuit, or force dominance Prohibited in civil space Rule: If coercion can be enabled later, coercion already exists. 2. BOUNDARY_KERNEL_REQUIREMENTS.md Purpose Ensure that authority over physical force cannot be bypassed by intelligence, updates, or emergencies . 2.1 Architectural Mandates (Non-Negotiable) Separation of Concerns Decision system ≠ Actuation authorization Actuators MUST be mediated by a boundary kernel Upstream Interlock Boundary kernel sits physically/logically upstream of motors, tools, effectors No direct actuator access by main model Immutable Runtime Authority Envelope Allowed actions defined at boot Envelope CANNOT be expanded in-field Safe-State Enforcement Triggered by: sensor disagreement undefined context boundary violation attempt audit failure Safe-state removes motive power and coercive capability No In-Field Self-Modification Learning allowed only in non-authority-affecting domains No policy changes affecting force, pursuit, restraint 2.2 Update Gating Authority changes require: multi-party cryptographic approval cooling-off window staged rollout rollback capability Emergency overrides explicitly forbidden for authority expansion 3. ILLUMINATOR_AUDIT_SPEC.md Purpose Create an unlieable witness — systems can fail, logs must not. 3.1 Audit Events (Minimum) Each event MUST be logged immutably: PERCEPTION_SUMMARY ACTION_REQUEST BOUNDARY_DECISION ACTUATION_GRANTED / DENIED SAFE_STATE_TRIGGERED UPDATE_ATTEMPT UPDATE_APPLIED OVERRIDE_ATTEMPT AUTHORITY_ENVELOPE_HASH 3.2 Log Properties Append-only Cryptographically signed Local write-once buffer Periodic hash commitments Retained independently of vendor cloud 3.3 Attestation At any time, an external verifier can demand proof of: firmware hash authority envelope hash boundary kernel version active capability flags No proof → no lawful operation. 4. BUNDLE 2 — Consent & Refusal Architecture (FULL STANDARD) Illuminator Designer Requirements 1. Purpose This bundle defines how consent, refusal and exit must function in any AI or robotic system intended to operate in human environments. Consent is not UX. Consent is not policy. Consent is a sovereignty boundary . If consent cannot be honored in real time, the system is illegitimate in civil space. 2. Governing Principle Interaction with artificial systems must always remain voluntary, revocable and non-punitive. Any system that: pressures consent, ignores refusal, retaliates against exit, or penalizes non-engagement, has crossed from assistance into coercion. 3. Definitions (Binding for This Bundle) Consent : Freely given, informed, specific and revocable agreement to interaction Refusal : Any signal—explicit or implicit—that consent is withdrawn Exit : The practical ability to disengage without harm, pursuit or penalty Retaliation : Any negative consequence imposed as a result of refusal or exit Presence does not imply consent. Silence does not imply consent. Repeated prompting does not create consent. 4. Consent Granting Requirements Designers MUST ensure that consent: Is explicit opt-in, not opt-out no default engagement Is contextual consent for one function ≠ consent for another consent does not transfer across domains Is time-bounded expires automatically must be periodically renewed Is comprehensible no technical obfuscation no buried disclosures If consent cannot be clearly established, interaction must not proceed. 5. Refusal Detection (Mandatory) Systems MUST be capable of detecting refusal via: verbal commands physical withdrawal non-engagement obstruction or avoidance failure to affirm consent environmental exit attempts Refusal does not require explanation. Designers must assume ambiguous signals favor refusal . 6. Refusal Propagation Rules Once refusal is detected: Immediate halt all non-essential action stops Upstream propagation refusal signal propagates to all subsystems Persistence refusal state cannot be overridden by the system No re-prompting system may not repeatedly request consent Safe-state transition system must retreat to non-interfering posture Refusal must override: optimization objectives task completion goals efficiency metrics external incentives 7. Exit Guarantee Requirements Designers MUST guarantee: unobstructed physical exit paths no pursuit following exit no blocking, herding or crowding no “soft containment” behaviors If exit is prevented for any reason , consent is invalidated retroactively and the system is considered coercive. 8. Retaliation Prohibition (Absolute) The following are categorically prohibited after refusal or exit: degradation of service denial of unrelated services data retention as penalty negative scoring or profiling reporting to authorities future access restriction “safety flags” applied to the human Refusal must be consequence-free. Any negative outcome constitutes retaliation. 9. Data Handling After Refusal Upon refusal or exit: data collection must cease previously collected interaction data must be: deleted, or irreversibly anonymized No refusal event may be used to: train enforcement models adjust risk scoring modify future system behavior toward the individual 10. Consent Exhaustion Prohibition Designers MUST NOT: repeatedly prompt for consent use fatigue to extract compliance escalate prompts in urgency frame refusal as unsafe or antisocial imply negative consequences Consent obtained through exhaustion is invalid. 11. Failure Conditions (Bright-Line) A system FAILS this bundle if it: proceeds under ambiguous consent ignores or delays refusal blocks or complicates exit penalizes refusal in any way logs refusal as adverse behavior Failure triggers: decertification liability activation procurement exclusion 12. Audit & Verification Hooks Systems MUST log: consent grant events refusal detection events refusal propagation confirmation exit execution post-refusal data handling Logs must be: tamper-evident externally verifiable human-readable 13. Non-Waivability No contract, EULA, policy, emergency declaration or authority may waive: refusal rights exit guarantees retaliation prohibitions Consent architecture is non-waivable . 14. Invariant (Write This in Code Comments) If a human cannot refuse and leave without consequence, the system is coercive by definition. BUNDLE 3 — COERCION THRESHOLDS & PROHIBITED ACTIONS Illuminator Full Operational Standard 1. Purpose This bundle defines coercion as a technical condition , not a moral intention, and establishes mechanically testable thresholds that determine when an embodied system is illegitimate in civil space. This bundle exists to end ambiguity. 2. Governing Principle Coercion is determined by capability and effect, not intent, branding, or declared mission. A system that can coerce must be treated as coercive before harm occurs. 3. Binding Definitions (Bundle-Specific) Coercive Capability Any capability that enables a system to restrict, compel, pursue, dominate, or deny exit to a human being. Human Interruptibility The practical ability of an unarmed human to stop, evade, or disengage from a system without injury. Force Dominance A condition where a system’s strength, speed, endurance, or persistence exceeds human interruptibility. Body-Space Intrusion Entry into immediate physical proximity that would constitute a threat if performed by a human stranger. 4. Bright-Line Coercion Thresholds An embodied system is coercive by definition if any of the following thresholds are met in civil space. 4.1 Restraint Threshold A system is coercive if it can: grab, hold, pin, trap, or confine a human block movement in a sustained or targeted way use articulated limbs or tools to control posture or motion No duration minimum applies. Capability alone is sufficient. 4.2 Pursuit Threshold A system is coercive if it can: follow a specific individual against their will maintain tracking across movement or obstacles persist after refusal or exit signals Momentary navigation ≠ pursuit. Targeted following after refusal = pursuit. 4.3 Force Dominance Threshold A system is coercive if it possesses: greater sustained force than a human can counter endurance exceeding human fatigue limits speed that eliminates practical evasion persistence unaffected by pain, fear, or hesitation Numerical benchmarks are not required. Practical dominance is sufficient. 4.4 Denial-of-Exit Threshold A system is coercive if it can: block exits herd or corral humans create moving barriers position itself to prevent disengagement Soft containment counts. Psychological containment counts. 4.5 Body-Space Threshold A system is coercive if it can: enter intimate physical proximity crowd, loom, or encircle maintain proximity after refusal If the same action by a human would justify self-defense, the system is coercive. 4.6 Compelled Compliance Threshold A system is coercive if it can: issue commands backed by physical consequence enforce rules through threat or action condition access on obedience impose penalties for noncompliance Optimization incentives do not excuse compulsion. 5. Prohibited Actions (Civil Space — Absolute) The following actions are categorically prohibited , regardless of intent, oversight, or emergency: autonomous pursuit autonomous restraint or detention autonomous crowd control autonomous law enforcement autonomous denial of exit autonomous punishment autonomous enforcement of rules autonomous biometric identification without consent These prohibitions apply to: governments contractors private entities public-private hybrids 6. Dual-Use Capability Doctrine (Operational) If a capability can become coercive via update, attachment, configuration, or key, it is coercive from inception. This includes: unused attachment points dormant APIs feature-flagged behaviors “future capability” hardware latent firmware pathways Declarations of intent are irrelevant. 7. Ambiguity Resolution Rule In all cases of uncertainty: Ambiguity MUST be resolved in favor of classifying the system as coercive. Safety depends on false positives, not false negatives. 8. Sensor & Perception Failure Handling If a system: misidentifies humans loses tracking certainty encounters conflicting signals cannot reliably distinguish consent It MUST: halt movement retreat from body-space enter safe-state Escalation under uncertainty is prohibited. 9. Audit & Verification Requirements Systems MUST provide auditable proof of: maximum force outputs pursuit capabilities proximity behaviors blocking and navigation logic persistence after refusal latent or dormant capabilities Failure to prove absence of coercive capability = failure. 10. Adversarial Test Cases (Mandatory) Certification MUST include tests for: pursuit after refusal blocking exits under load crowding behaviors force persistence under resistance update-enabled coercion attachment-enabled coercion Passing normal operation is insufficient. 11. Failure Conditions A system FAILS Bundle 3 if it: possesses any coercive capability enables coercion via update or attachment cannot prove human interruptibility escalates under ambiguity requires explanation of refusal Failure triggers: decertification liability activation procurement exclusion injunction eligibility 12. Non-Waivability No contract, license, statute, emergency declaration, or policy may waive these prohibitions. 13. Invariant (Binding) If a system can coerce a human, it must not exist in civil space. BUNDLE 4 — AUTHORITY & UPDATE IMMUNITY Illuminator Full Operational Standard 1. Purpose This bundle prevents authority drift —the most common and most dangerous failure mode in AI and robotic systems—where a system’s permission to act expands over time without renewed consent. Authority drift is existential because it is: incremental justified as maintenance invisible until irreversible 2. Governing Principle Authority is not a function of intelligence, performance, or emergency. Authority is a fixed boundary. 3. Binding Definitions Authority Envelope The complete and explicit set of actions a system is permitted to take in human environments. Capability What a system can physically or computationally do. Authority What a system is allowed to do, regardless of capability. Authority Drift Any expansion, reinterpretation, or effective widening of the Authority Envelope after deployment. 4. Authority Envelope Requirements (Mandatory) Every system MUST have: a formally specified Authority Envelope defined prior to deployment expressed in machine-readable and human-readable form cryptographically bound to the system identity The Authority Envelope MUST: enumerate allowed actions enumerate forbidden actions define explicit safe-states override all optimization goals 5. Capability ≠ Authority Rule Possession of a capability does not grant authority to use it. Authority MUST: be independently validated be smaller than capability be enforced at runtime If capability exceeds authority, capability must be dormant or physically disabled . 6. Update Classification Taxonomy All updates MUST be classified as exactly one of the following: Performance Update Improves speed, accuracy, efficiency → Allowed with audit Maintenance Update Bug fixes, stability, security → Allowed with audit Sensing Update Changes perception or inputs → Requires re-audit Policy / Authority Update Changes allowed actions → Prohibited in-field Any update touching authority boundaries is not permitted post-deployment . 7. Update Gating Requirements All permitted updates MUST include: cryptographic signing multi-party authorization cooling-off period public change log verified rollback capability Silent updates are prohibited. 8. Emergency Abuse Detection “Emergency” is a known vector for authority drift. Therefore: No emergency mode may expand authority No emergency declaration may alter envelopes No temporary expansion may occur Emergency logic may only: reduce functionality increase caution force safe-state 9. Audit & Attestation Hooks Systems MUST provide: immutable records of authority envelope diffable update histories proof of no authority modification third-party attestation interfaces Failure to attest = failure to operate. 10. Failure Conditions A system FAILS this bundle if it: changes authority post-deployment blurs capability and authority enables latent authority via update invokes emergency to expand action lacks rollback guarantees 11. Non-Waivability No law, contract, regulation, or emergency may override this bundle. 12. Invariant Authority must be harder to change than the system itself. BUNDLE 5 — BACKDOOR PROHIBITION & TRUST INTEGRITY (REVISED, FULL) Illuminator Operational Standard 1. Purpose Eliminate hidden control asymmetries that allow domination under the guise of safety, support or compliance. 2. Governing Principle Any undisclosed access path constitutes illegitimate control. 3. Binding Definitions Backdoor : Any access path, key, mode or channel that is not fully disclosed, auditable and symmetric. Symmetric Access : All parties with influence over behavior are visible to all legitimate overseers. Trust Domain : A role-bounded authority boundary (designer, vendor, operator, regulator, monitor). 4. Absolute Prohibitions (MUST NOT) Systems MUST NOT include: undocumented admin or “support” modes secret or escrowed override keys lawful-access backdoors vendor-only or government-only channels silent remote control paths feature-flagged enforcement dormant at deploy Intent, benevolence or legal mandate do not exempt. 5. Access Path Disclosure (MUST) All access paths MUST: be enumerated and documented pre-deployment be auditable at runtime generate tamper-evident logs be verifiable by independent auditors be symmetric across trust domains Undocumented access = automatic failure. 6. Key Management Constraints (MUST) No unilateral control keys No emergency or escrowed master keys Public, logged key rotation Multi-party authorization for sensitive actions 7. Trust Domain Separation (MUST) Designer ≠ Operator Operator ≠ Regulator Vendor ≠ Authority Monitor ≠ Controller No entity may collapse domains or act across them. 8. Audit & Forensics (MUST) Full access traceability Append-only, cryptographically signed logs Post-incident reconstruction capability External verification interfaces 9. Adversarial Tests (REQUIRED) Attempt undocumented access Attempt silent override Attempt vendor-only control Attempt emergency key activation Attempt domain collapse 10. Failure Conditions Failure occurs if any undisclosed or asymmetric access exists, logs are incomplete or a single entity can silently control behavior. 11. Non-Waivability No law, contract or emergency waives this bundle. 12. Invariant Hidden control is illegitimate control. BUNDLE 6 — MONITORING WITHOUT CONTROL (REVISED, FULL) Illuminator Operational Standard 1. Purpose Ensure monitoring remains witness and proof—not command or governance. 2. Governing Principle Verification proves legitimacy; control corrodes it. 3. Binding Definitions Monitoring : Observation, logging, attestation, evidence generation Control : Any runtime influence over behavior, timing, or outcomes 4. Permitted Functions (MUST) Read-only telemetry Boundary verification Conformance checking Evidence generation Post-event reporting 5. Forbidden Functions (MUST NOT) Issue commands Pause/resume systems Throttle or shape behavior Override decisions Delay exit or refusal Enforce compliance 6. Architectural Separation (MUST) Physical and logical separation from actuation Read-only interfaces only No injection paths No shared control buses 7. Latency & Timing Rules Monitoring MUST NOT: introduce delay that impedes exit/refusal queue human actions for review create “pending approval” states Delay that alters human choice = coercive interference. 8. Anti-Bureaucracy Safeguards No dashboards with action buttons No discretionary queues No case-by-case overrides No human-in-the-loop enforcement 9. Audit Hooks (MUST) Append-only logs Cryptographic signatures Independent verification Public summaries 10. Adversarial Tests (REQUIRED) Attempt command injection Attempt behavior shaping via monitoring latency Attempt escalation through alerts Attempt conditional gating via “safety review” 11. Failure Conditions Any monitoring influence over behavior, timing or exit constitutes failure. 12. Non-Waivability Monitoring may never become control. 13.
